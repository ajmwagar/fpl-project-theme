# FPL documentation updates

Maintain accurate canonical Markdown and reproducible published documentation.
Use existing owner tools; correct interface and model facts at their source.

## Find the owners

Locate the `fpl-project-theme` checkout and the requested site's checkout. Read
applicable `AGENTS.md`, the publisher's README, and the site's publication
manifest rather than assuming a machine path or frozen revision:

- `fungos-web/docs.tsv`: fungOS guides and UMIE, Unibus and DCP pages.
- `holodeck/website-docs.tsv`: Holodeck's Lua guide.
- Manifest rows identify canonical Markdown, HTML output, site root, project ID,
  source repository URL and explicit code checkout/URL. Paths are relative to the
  manifest; project IDs and themes come from the publisher registry.

Canonical content is in `docs-source/` or `website-docs-source/`. Site HTML,
adjacent `.md` exports and `theme/` are generated. Do not hand-edit those files.
Keep owner documentation and executable examples authoritative; the public site
is a projection, not an alternative protocol or application implementation.

## Update and verify

1. Identify the requested guide and relevant owning implementation. Inspect
   changes, schemas, examples, tests and existing evidence. Preserve unrelated
   worktree changes. Keep public prose free of credentials, private addresses and
   unpublished operational/training details. Verify example commands where
   practical; label hardware-, service- or access-dependent checks not performed.
2. Edit canonical Markdown. Distinguish implemented behavior, recorded tests and
   planned work. Explain prerequisites, expected results and useful failure or
   recovery steps when writing a runbook. Derive mechanical inventories from
   their owning generators instead of maintaining parallel tables.
3. For UMIE model changes, read [references/umie.md](references/umie.md) and run
   its catalog/projection workflow before rendering. It updates the marked
   matrix block only; keep the explanatory prose accurate too.
4. Preserve `source_commit` and `watches` as explicit code-review evidence.
   Compare watched changes to the recorded baseline; advance that baseline only
   after actually reviewing the affected claims and verification evidence.
   Neither regeneration nor a schema pass establishes a fresh hardware result.
5. Commit verified canonical Markdown before rendering: the publisher obtains
   the last documentation commit, subject and date from that file's Git history.
   Generated-only commits must not change that provenance. Commit theme source
   changes before installing a new theme revision.
6. Generate the selected pages and install the shared theme. Read
   [references/publication.md](references/publication.md) for commands, manifest
   behavior, freshness gates and verification. Check exact Markdown exports,
   links, code examples and Copy for LLM behavior. Run relevant tool tests if
   their implementation changed, then commit the generated artifacts.

`--check` verifies generated bytes; `--fail-on-stale` separately rejects changed
or dirty watched code. A stale page may remain explicitly documented against
its older reviewed revision when that matches the task. Report the warning and
its cause; never relabel it current merely to pass a gate. Missing watched paths,
invalid baselines and generation errors require resolution, not silent bypasses.

## Finish within scope

Local commits are authorized by the FPL tenets; pushing, releasing and deploying
need task or existing session authorization. Honor authorization already given.
Check branch history before pushing so unrelated unpublished source work is not
included accidentally. A pushed commit or working local preview does not prove
live publication. Use the hosting owner's supported workflow when deployment is
requested; do not invent endpoints or replace scoped credentials with admin ones.

Report changed guides, catalog/evidence scope, checks, commit/publication state,
and material stale or unverified items. Include useful preview links if available.
